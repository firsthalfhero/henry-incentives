# Henry's Weekly Earning Chart

A Montessori-informed "earned income" incentive chart for George's son Henry (~10). Tracks three activities — Violin, Schoolwork, Reading — each on its own independent Mon–Sun calendar, with escalating pay for consistency and a weekly spending cap. Built as a small Netlify site: a static HTML page backed by one Netlify Function and Netlify Blobs for shared storage.

Full design history, rationale, and open decisions live in George's Claude project ("Parenting Incentives"), doc `claude/montessori-incentive-scheme-draft.md`. This file is about the code; that doc is about the *why*.

```
  henry-earning-chart.html         ← OLD single-device version (localStorage-based).
                                      Superseded by site/ below — kept only as a snapshot.
  site/                            ← the live project. Run all `netlify`/`npm` commands from here.
    index.template.html            ← the chart's source. Committed to git. Contains the
                                      placeholder __CHART_API_KEY__ instead of a real key.
    index.html                     ← GENERATED by build.mjs — the file Netlify actually
                                      publishes. Git-ignored. Never edit this one directly;
                                      edit index.template.html and rebuild.
    build.mjs                      ← the build step: substitutes CHART_API_KEY (from
                                      Netlify's environment variables) into index.template.html
    package.json                   ← declares the @netlify/blobs dependency + "build" script
    netlify.toml                   ← command = "node build.mjs", publish = ".", functions = "netlify/functions"
    netlify/functions/state.mjs    ← the one API endpoint, mounted at /api/state
```

## Architecture

The chart is intentionally stateless on the client: it holds no data of its own, so any
device that opens the link sees the same live state. `index.html`'s script does three
things, all against `/api/state?key=<API_KEY>`:

- **On load** — `GET /api/state` → `{ week, ticks }`, then renders.
- **On tapping a day** — optimistic UI flip, then `POST { action: "tick", activity, day }`.
- **On "Reset week"** (only shown when the page URL has `?parent=1`) — `POST { action: "reset" }`.

`netlify/functions/state.mjs` is the only backend code. It stores one JSON document in a
Netlify Blobs store (`getStore("henry-chart")`, key `"state"`):

```json
{
  "week": "2026-W36",
  "ticks": { "violin": [false,...7], "school": [...], "reading": [...] },
  "history": [
    { "timestamp": "2026-09-04T10:32:00Z", "week": "2026-W35", "total": 45.00, "spend": 40.00, "savings": 5.00 }
  ]
}
```

- Every request (GET and POST) must include `?key=` matching the `CHART_API_KEY`
  environment variable, or it gets a 401. **This is a convenience gate, not real
  security** — the key still ends up visible in the deployed page's source (the browser
  has to send it), same spirit as the `?parent=1` link gate. It exists only so the
  endpoint isn't trivially stumbled on. What the templating below buys you is keeping the
  key out of **git**, not out of the deployed page.
- On every GET, the function checks whether the stored `week` still matches the real
  current ISO week (Mon-start). If not, it quietly rolls over to a fresh empty week —
  **no history entry is written for this natural rollover**, only an explicit reset does
  that.
- On `reset`, the *server* (not the client) recomputes that week's total/spend/savings
  from the stored ticks — using the same `RATES`/`SPEND_CAP` constants duplicated at the
  top of `state.mjs` (must be kept in sync with the matching constants in
  `index.template.html`'s `<script>`) — appends a history entry, clears ticks, and
  advances the week.
- History is written but **never returned to the client** and **never shown in the UI**,
  per George's explicit preference. To read it, use the Netlify CLI directly:
  `netlify blobs:get henry-chart state --output state.json` (run from `site/`).

## The CHART_API_KEY build step

The real key value lives in exactly one place: the `CHART_API_KEY` environment variable
on the Netlify site (set via `netlify env:set`, or the Netlify UI). Nothing in git ever
contains the real value — `index.template.html` has the literal placeholder text
`__CHART_API_KEY__` where the key goes.

`build.mjs` reads `index.template.html`, replaces `__CHART_API_KEY__` with
`process.env.CHART_API_KEY`, and writes the result to `index.html` — the file
`netlify.toml`'s `publish = "."` actually serves. This runs automatically on every
Netlify deploy (`[build] command = "node build.mjs"`). To run it yourself locally, use
`netlify build` (not plain `node build.mjs`) so Netlify CLI pulls the env var in from the
linked site rather than needing it exported in your own shell — see Local dev below.

If you ever need to rotate the key: `netlify env:set CHART_API_KEY <new value>`, then
redeploy (`netlify deploy --prod`, or push to `master` if the repo is git-linked — see
Deploying below). No code or template change needed.

## Rates, tiers, cap (must match in both `index.template.html` and `state.mjs`)

- `RATES = [2.00, 2.50, 3.00, 3.50, 4.00, 4.50, 5.00]` — one per activity, day 1..7 of
  that activity's week (Monday first). Max $24.50/activity/week.
- Tiers, per activity, by how many days of *that activity* are ticked so far this week:
  days 1–3 = Tier 1 "Getting going" (cool slate), days 4–5 = Tier 2 "Weekly target"
  (gold), days 6–7 = Tier 3 "Bonus" (plum, dashed border).
- `SPEND_CAP = 40` — anything earned over $40/week across all activities combined goes
  to savings instead of spending money.
- Three activities run fully independently (not pooled) — this was a deliberate fix so
  Henry can't hit his weekly target using only two activities and skip violin.

## Local dev

```
cd site
npm install
netlify login      # first time only
netlify init        # first time only — creates & links the Netlify site
netlify env:set CHART_API_KEY <the value you want to use>
netlify build        # generates index.html from index.template.html, pulling
                      # CHART_API_KEY in from the linked Netlify site
netlify dev
```

Open the printed `http://localhost:8888` URL — do **not** open `index.html` directly by
double-clicking it (`file://` has no server behind it, so `/api/state` can't resolve and
the page shows "Couldn't load the chart"). If you edit `index.template.html`, re-run
`netlify build` before refreshing — `netlify dev` doesn't re-run the build step
automatically, it just serves whatever `index.html` currently contains.

## Deploying

```
cd site
netlify deploy --prod
```

This runs `node build.mjs` as part of the deploy (per `netlify.toml`), so it always
publishes a freshly-generated `index.html` with the current `CHART_API_KEY` baked in —
you never need to run the build step separately before deploying.

Use the plain production URL it prints (`https://<site-name>.netlify.app`), not the
hash-prefixed "unique deploy" URL — the hash one still works, but it's a per-deploy
address, not the stable one to bookmark/share.

Environment variables (`CHART_API_KEY`) must be set on the linked site *before* deploying,
and if things seem to work locally but a live deploy 401s, re-check with
`netlify env:list` and redeploy after fixing it.

If the site is linked to GitHub for continuous deployment (Site configuration → Build &
deploy → Continuous deployment, base directory `site`), a plain `git push` to `master`
triggers the same build-and-deploy automatically — no `netlify deploy` needed.

## Known issues already hit & fixed (for context, not currently broken)

- **`Cannot find package '@netlify/blobs'` (500 on every request in `netlify dev`)** —
  caused by `npm install` never having been run (or not completing) inside `site/`.
  Fix: `npm install` from `site/`, confirm `node_modules/@netlify/blobs` exists, restart
  `netlify dev`.
- **`No project id found, please run inside a project folder or 'netlify link'`** when
  running `netlify env:set` — the folder wasn't linked to a Netlify site yet. Fix:
  `netlify init` (or `netlify link` if a site already exists) from inside `site/` first.
- **401 on `/api/state` after deploying** — `CHART_API_KEY` wasn't set on the linked site
  before the deploy that's being tested, or was set but that deploy predates it. Fix:
  `netlify env:list` to confirm the key and value are present, then `netlify deploy --prod`
  again and test the plain production URL.
- **Tapping a second day cancelled the first** — a lost-update race caused by Netlify
  Blobs' default eventually-consistent reads. Fixed in `state.mjs` by using
  `getStore({ consistency: "strong" })` plus a compare-and-swap (ETag) retry loop on every
  write, so concurrent taps from different devices can't silently overwrite each other.
- **The real API key was briefly committed in plain text** (in `index.html`, before the
  template/build-step split above existed) — caught before the repo was ever pushed to
  GitHub, so the initial commit was rewritten rather than needing a history purge. If you
  ever find the literal key value in a tracked file again, treat it the same way: fix it
  and rewrite history before pushing, rather than adding a new commit on top.

## Things to keep in sync when editing

Any change to the rate table, tier boundaries, or spending cap needs to be made in
**both** `site/index.template.html` (the `<script>` block near the top: `RATES`,
`SPEND_CAP`) and `site/netlify/functions/state.mjs` (top of file: same constants) —
they're intentionally duplicated rather than shared, since the server independently
recomputes totals for the reset history rather than trusting the client.

The old `henry-earning-chart.html` (single-device, localStorage-based) and the
Claude-hosted artifact it was published from are both stale snapshots now that `site/` is
the canonical, shared version. Don't edit them expecting it to affect the live chart.
