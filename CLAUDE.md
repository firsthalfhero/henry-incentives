# Henry & Sophie's Weekly Earning Charts

A Montessori-informed "earned income" incentive chart, one per child. Each child tracks
2–6 configurable activities on their own independent Mon–Sun calendars, with escalating
pay for consistency (in tiers, not per-tick) and a weekly spending cap. Built as two
independent Netlify sites sharing one git repo: a static HTML page and Netlify Function
mechanism that's genuinely shared, with only activities/rates/theme/name differing per
child.

Full design history, rationale, and open decisions live in George's Claude project ("Parenting Incentives"), doc `claude/montessori-incentive-scheme-draft.md`. This file is about the code; that doc is about the *why*.

## Directory layout

```
henry-incentives/

  montessori-incentive-scheme.md   ← design doc, mirrors the Claude project doc
  henry-earning-chart.html         ← OLD single-device version (localStorage-based).
                                      Stale snapshot, kept for history only.

  core/                            ← SHARED. Edit here, redeploy both children, done.

                                      placeholders __CHART_API_KEY__ and

    build.mjs                        the build step — see "The build step" below.
    lib/
      state-core.mjs                 the actual tick/reset/rollover/rate logic, as a
                                      `makeHandler({ activitiesData, storeName, getStore })`

                                      "Architecture" below for why that matters.

  children/
    henry/                          ← Henry's site. Run all `netlify`/`npm` commands here
                                      for Henry. Independent Netlify site, own URL, own
                                      CHART_API_KEY, own Blobs store ("henry-chart").
      activities.json                 Henry's activities/rates/cap/name. Single source of
                                      truth for his chart. See "Activities" below.
      theme.css                       Henry's colour palette (flat --var: value; lines).
      netlify.toml                    command = "node ../../core/build.mjs", publish = ".",
                                      functions = "netlify/functions"
      package.json                    declares the @netlify/blobs dependency
      netlify/functions/state.mjs     thin wrapper — imports activities.json + getStore
                                      locally, imports the shared factory from core/, and
                                      calls makeHandler({ ..., storeName: "henry-chart" })
      index.html                     ← GENERATED by build.mjs. Git-ignored. Never edit
                                      directly.
    sophie/                          ← Sophie's site. Same shape as henry/, entirely
                                      independent Netlify site/URL/key/store
                                      ("sophie-chart"). Currently placeholder content —
                                      see "Activities" below.
```

`core/` is never itself a Netlify site (no `netlify.toml` there) — it's pure shared
source each child's build/function reaches into via relative paths.

## Architecture

Each chart is intentionally stateless on the client: it holds no data of its own, so any
device that opens that child's link sees the same live state for that child. The page's
script does three things, all against `/api/state?key=<API_KEY>`:

- **On load** — `GET /api/state` → `{ week, ticks }`, then renders.
- **On tapping a day** — optimistic UI flip, then `POST { action: "tick", activity, day }`.
- **On "Reset week"** (only shown when the page URL has `?parent=1`) — `POST { action: "reset" }`.

The actual logic — rate/tier math, tick/reset handling, the Blobs compare-and-swap retry
loop, the weekly rollover, the spend-cap-vs-savings split — lives in exactly one place,
`core/lib/state-core.mjs`, as a `makeHandler({ activitiesData, storeName, getStore })`
factory. Each child's own `netlify/functions/state.mjs` is a thin wrapper: it imports
`getStore` from `@netlify/blobs` **itself** (not from `core/`) and that child's own
`activities.json`, then calls the shared factory:

```js
import { getStore } from "@netlify/blobs";
import activitiesData from "../../activities.json" with { type: "json" };
import { makeHandler } from "../../../../core/lib/state-core.mjs";

export default makeHandler({ activitiesData, storeName: "henry-chart", getStore });
export const config = { path: "/api/state" };
```

**Why `state-core.mjs` has no npm dependencies of its own:** each child is a separate
Netlify site with its own base directory (`children/henry`, `children/sophie`), and
Netlify's `npm install` step only installs what that base directory's own `package.json`
declares. If the shared factory imported `@netlify/blobs` directly, that import would sit
outside every child's base directory and have no `node_modules` to resolve against. So
`state-core.mjs` takes `getStore` as a parameter instead — dependency injection — and
each child's wrapper supplies it from its own, already-working `npm install`. The plain
relative import of `state-core.mjs` itself (a dependency-free file) reaching outside the
child's base directory is unrelated to this and just works: Netlify's esbuild-based
Functions bundler resolves relative imports by filesystem path, not confined to "base
directory" (confirmed against a real deploy — see git history around the multi-child
restructure for the spike that verified this before it was relied on).

**Don't "helpfully" inline `@netlify/blobs` into `state-core.mjs` or move it there** — it
would silently break Functions bundling for whichever child's base directory doesn't
happen to have it hoisted.

`state-core.mjs` stores one JSON document per child in that child's own Netlify Blobs
store (`getStore({ name: storeName })`, key `"state"`):

```json
{
  "week": "2026-W36",
  "ticks": { "violin": [false,...7], "school": [...], "reading": [...] },
  "history": [
    { "timestamp": "2026-09-04T10:32:00Z", "week": "2026-W35", "total": 45.00, "spend": 40.00, "savings": 5.00 }
  ]
}
```

- Every request (GET and POST) must include `?key=` matching that child's own
  `CHART_API_KEY` environment variable, or it gets a 401. **This is a convenience gate,
  not real security** — the key still ends up visible in the deployed page's source (the
  browser has to send it), same spirit as the `?parent=1` link gate. It exists only so the
  endpoint isn't trivially stumbled on. What the templating below buys you is keeping the
  key out of **git**, not out of the deployed page.
- On every GET, the function checks whether the stored `week` still matches the real
  current ISO week (Mon-start). If not, it quietly rolls over to a fresh empty week —
  **no history entry is written for this natural rollover**, only an explicit reset does
  that.
- On `reset`, the *server* (not the client) recomputes that week's total/spend/savings
  from the stored ticks — using the same rate schedule (from that child's
  `activities.json`'s `baseRate`/`increment`/`spendCap`, per-activity `multiplier`) —
  appends a history entry, clears ticks, and advances the week.
- History is written but **never returned to the client** and **never shown in the UI**,
  per George's explicit preference. To read it, use the Netlify CLI directly from that
  child's directory: `netlify blobs:get henry-chart state --output state.json` (run from
  `children/henry`) or `netlify blobs:get sophie-chart state --output state.json` (from
  `children/sophie`).

## Activities (`activities.json`)

Each child's activities/rates/cap/name live in `children/<name>/activities.json`,
published as a static file (so it's fetched at `/activities.json`) and also imported
directly by that child's `state.mjs`. It's the single source of truth for that child:
nothing about their activities or pay schedule is hardcoded in `index.template.html` or
`state-core.mjs`.

The file is one JSON object, not a bare array:

```json
{
  "childName": "Henry",
  "baseRate": 2.00,
  "increment": 0.50,
  "spendCap": 40,
  "activities": [
    {
      "key": "reading",       // stable id — used as the ticks key, must be unique
      "name": "Reading",      // shown as the card title and calendar row label
      "duration": "1 hour",   // free text next to the clock icon
      "note": "a proper stretch — you'll need to start before \"reading time\"",
      "color": "#3F7D53",     // card border / accent colour (hex)
      "tint": "#DEEBE1",      // card background (hex, a pale version of color)
      "multiplier": 1,        // optional, default 1 — see "Pay rate & multiplier" below
      "icon": "<svg viewBox=\"0 0 34 40\" fill=\"none\">...</svg>"   // optional
    }
  ]
}
```

- `childName` drives the page `<title>` and eyebrow text, set client-side once this file
  loads (see `loadActivities()` in `index.template.html`).
- `spendCap` replaces what used to be a hardcoded `SPEND_CAP` constant — see "Rates,
  tiers, cap" below. Every `$<cap>` mention in the page copy (the intro paragraph, the
  savings note, both accordions) is a `<span class="cap-amount">` populated from this
  value — the template itself names no dollar figure or activity by name, so it reads
  correctly for any child.
- **2 to 6 activities** are supported, listed under `activities`. `index.template.html`
  fetches the file client-side and renders both the "ways to earn" cards and the calendar
  rows from it; each child's `state.mjs` passes it into `makeHandler()`, which derives its
  own activity-key list from `activitiesData.activities`, capped at 6 with `.slice(0, 6)`
  as a safety net. Add, remove, or reorder a child's activities by editing their one file
  — no other code changes needed as long as each `key` is unique.
- The card grid is responsive: 2 or 3 activities show in that many columns; 4 shows as
  2×2; 5 or 6 show as rows of 3. This is computed in `index.template.html`'s
  `earnerColumns()` function.
- **`icon` is optional.** Leave it out (or set it to `null`/`""`) for an activity and both
  the card and the calendar row simply render without one — no broken layout, no
  "undefined" text. Icons are inline SVG strings using `viewBox="0 0 34 40"`, sized by CSS
  (`.earner svg` / `.cal-row-label svg`), with the stroke colour baked in as a literal hex
  value (not a CSS variable) so any activity's icon is self-contained regardless of its
  colour.
- **Sophie's `activities.json` is currently placeholder content** — two example
  activities literally named "PLACEHOLDER — replace me", with guessed `baseRate`/
  `increment`/`spendCap`. Edit `children/sophie/activities.json` with her real activities,
  colours, and icons the same way Henry's is edited; no other code changes needed.

### Pay rate & multiplier

- `baseRate` and `increment` (top-level, per child) define a pay schedule that steps up
  once per tier, not once per tick: the 1st–3rd time that activity is ticked in a week
  (Tier 1) pays `baseRate`, the 4th–5th time (Tier 2) pays `baseRate + increment`, the
  6th–7th time (Tier 3) pays `baseRate + 2 × increment`. With Henry's defaults ($2.00
  base, $0.50 increment) that's $2.00 for the first three, $2.50 for the next two, $3.00
  for the last two. Change `baseRate` to shift the whole schedule up or down; change
  `increment` to make the jump between tiers bigger or smaller.
- Each activity's own `multiplier` scales its result: `1` (or omitting the field) is the
  standard rate, `1.5` pays that activity 50% more than the schedule, `0.5` pays half. It
  applies to every tier of that activity independently.
- Both the client (`index.template.html`, in `buildRates()`/`computeRow()`) and the server
  (`state-core.mjs`, in `buildRates()`/`computeTotals()`) derive their rate table and
  apply the multiplier the same way from that child's `activities.json` — this is not
  duplicated by hand. The one thing still hand-duplicated is the tier *boundaries*
  themselves (ranks 0-2/3-4/5-6) — see "Things to keep in sync" below.

## The build step

The real `CHART_API_KEY` value lives in exactly one place per child: that child's own
`CHART_API_KEY` environment variable on their Netlify site (set via `netlify env:set`, or
the Netlify UI). Nothing in git ever contains a real key — `core/index.template.html` has
the literal placeholder text `__CHART_API_KEY__` where it goes.

`core/build.mjs` is invoked as `node ../../core/build.mjs` from inside a child's own
directory (that's each child's `netlify.toml` `[build] command`, run with Netlify's base
directory set to that child, so `process.cwd()` at run time is the child's own folder).
It reads the ONE shared `index.template.html` (relative to its own file location, i.e.
always `core/`, regardless of which child invoked it), reads that child's own `theme.css`
from `process.cwd()`, substitutes `__CHART_API_KEY__` with the real key from the
environment and `/* __THEME_VARS__ */` with the child's theme file's contents verbatim,
and writes `index.html` into that child's own directory — the file `netlify.toml`'s
`publish = "."` actually serves.

This runs automatically on every Netlify deploy. To run it yourself locally, use
`netlify build` from inside the child's directory (not plain `node ../../core/build.mjs`)
so Netlify CLI pulls the env var in from that child's linked site rather than needing it
exported in your own shell — see Local dev below.

If you ever need to rotate a child's key: `netlify env:set CHART_API_KEY <new value>`
from inside their directory, then redeploy. No code or template change needed.

### Theming (`theme.css`)

Each child's `theme.css` is a flat list of `--var: value;` lines — the *complete* palette
(all 16 vars), no partial-override cascade to reason about. `core/index.template.html`'s
`:root{}` block contains only the marker `/* __THEME_VARS__ */`, which `build.mjs`
replaces with that child's file verbatim. This is palette-only theming — fonts, layout,
and the card/calendar structure are identical for every child by design; only colours
differ. The 16 vars: `--paper`, `--paper-deep`, `--line`, `--ink`, `--ink-soft`, `--gold`,
`--gold-tint`, `--focus` (the keyboard focus-ring colour), `--savings`, `--tier1`,
`--tier1-tint`, `--tier1-line`, `--tier3`, `--tier3-tint`, `--error`, `--error-tint`.

## Rates, tiers, cap

- The per-tier rate schedule comes from each child's own `activities.json`
  `baseRate`/`increment` (see "Pay rate & multiplier" above), scaled per activity by its
  `multiplier`.
- Tiers, per activity, by how many days of *that activity* are ticked so far this week:
  days 1–3 = Tier 1 "Getting going" (cool slate), days 4–5 = Tier 2 "Weekly target"
  (gold), days 6–7 = Tier 3 "Bonus" (plum, dashed border). These boundaries drive both the
  pay schedule and the display colour, via `tierFor()` in `index.template.html` and
  `tierIndexFor()` in `state-core.mjs` — see "Things to keep in sync" below. Tiers are
  based on which day it is, not the dollar amount, so they're unaffected by `multiplier`.
- `spendCap` (per child, from their `activities.json`) — anything earned over that
  amount/week across *all* of that child's activities combined goes to savings instead of
  spending money. Unlike before, this is **not** a hand-duplicated constant any more: both
  the client and `state-core.mjs` read it from the same `activitiesData.spendCap` (with a
  `40` fallback if it's ever omitted).
- All activities run fully independently (not pooled) — ticking one doesn't cover
  skipping another; each has its own weekly rate schedule.

## Local dev

```
cd children/henry     # or children/sophie
npm install
netlify login      # first time only
netlify link        # first time only — links to that child's existing Netlify site
                     # (use `netlify init` instead, from this same directory, to create
                     # a brand-new child's site for the first time)
netlify env:set CHART_API_KEY <the value you want to use>
netlify build        # generates index.html via core/build.mjs, pulling
                      # CHART_API_KEY in from the linked Netlify site
netlify dev
```

Open the printed `http://localhost:8888` URL — do **not** open `index.html` directly by
double-clicking it (`file://` has no server behind it, so `/api/state` can't resolve and
the page shows "Couldn't load the chart"). If you edit `core/index.template.html` (or
that child's `activities.json`/`theme.css`), re-run `netlify build` before refreshing —
`netlify dev` doesn't re-run the build step automatically, it just serves whatever
`index.html` currently contains.

**Editing `core/` affects both children** but only once each has been rebuilt/redeployed
— there's no live link between them. After a `core/` change, rebuild and redeploy
*both* `children/henry` and `children/sophie` to keep them in sync.

## Deploying

```
cd children/henry     # or children/sophie — deploy each independently
netlify deploy --prod
```

This runs `core/build.mjs` as part of the deploy (per that child's `netlify.toml`), so it
always publishes a freshly-generated `index.html` with the current `CHART_API_KEY` and
`theme.css` baked in — you never need to run the build step separately before deploying.

Use the plain production URL it prints (`https://<site-name>.netlify.app`), not the
hash-prefixed "unique deploy" URL — the hash one still works, but it's a per-deploy
address, not the stable one to bookmark/share.

Environment variables (`CHART_API_KEY`) must be set on that child's linked site *before*
deploying, and if things seem to work locally but a live deploy 401s, re-check with
`netlify env:list` (from inside that child's directory) and redeploy after fixing it.

If a child's site is linked to GitHub for continuous deployment (Site configuration →
Build & deploy → Continuous deployment, base directory `children/henry` or
`children/sophie`), a plain `git push` to `main` triggers the same build-and-deploy
automatically for whichever child(ren) are linked that way — no `netlify deploy` needed.
**A `core/` edit alone won't trigger anything unless a child's own files also change in
the same push** — if you only touched `core/`, trigger both children's deploys manually
(`netlify deploy --prod` from each) or make a trivial touch to each child's tracked files.

## Known issues already hit & fixed (for context, not currently broken)

- **`Cannot find package '@netlify/blobs'` (500 on every request in `netlify dev`)** —
  caused by `npm install` never having been run (or not completing) inside that child's
  directory. Fix: `npm install` from the child's directory, confirm
  `node_modules/@netlify/blobs` exists, restart `netlify dev`.
- **`No project id found, please run inside a project folder or 'netlify link'`** when
  running `netlify env:set` — the folder wasn't linked to a Netlify site yet. Fix:
  `netlify init` (new site) or `netlify link` (existing site) from inside that child's
  directory first.
- **401 on `/api/state` after deploying** — `CHART_API_KEY` wasn't set on that child's
  linked site before the deploy being tested, or was set but that deploy predates it. Fix:
  `netlify env:list` (from that child's directory) to confirm the key and value are
  present, then `netlify deploy --prod` again and test the plain production URL.
- **Tapping a second day cancelled the first** — a lost-update race caused by Netlify
  Blobs' default eventually-consistent reads. Fixed in `state-core.mjs` by using
  `getStore({ consistency: "strong" })` plus a compare-and-swap (ETag) retry loop on every
  write, so concurrent taps from different devices can't silently overwrite each other.
- **The real API key was briefly committed in plain text** (in `index.html`, before the
  template/build-step split above existed) — caught before the repo was ever pushed to
  GitHub, so the initial commit was rewritten rather than needing a history purge. If you
  ever find the literal key value in a tracked file again, treat it the same way: fix it
  and rewrite history before pushing, rather than adding a new commit on top.
- **`Base directory does not exist: .../site`** — a leftover artifact from before the
  multi-child restructure (Netlify's own remembered dev-server framework detection for
  the site can lag behind a directory rename). Harmless — `netlify dev` falls back to a
  plain static server and works fine regardless; if it bothers you, it should clear up
  after that child's next full `netlify deploy --prod`.

## Things to keep in sync when editing

The tier boundaries (ranks 0-2 / 3-4 / 5-6, i.e. "days 1-3 / 4-5 / 6-7") are the one thing
still hand-duplicated: `tierFor()` in `core/index.template.html` and `tierIndexFor()` in
`core/lib/state-core.mjs` both encode the same three ranges independently, since the
server independently recomputes totals for the reset history rather than trusting the
client. Both now live in `core/`, so there's only one copy of each per role (client,
server) rather than one per child — but they're still two separate functions that must
agree with each other.

Everything else — the activity list, `baseRate`, `increment`, `spendCap`, `childName`,
and each activity's `multiplier` — is **not** duplicated: both the client and that
child's `state.mjs` read it from that child's own `activities.json`. Theme colours are
similarly not duplicated in code — each child's `theme.css` is the one place their
palette is defined.

The old `henry-earning-chart.html` (single-device, localStorage-based) and the
Claude-hosted artifact it was published from are both stale snapshots now that
`children/henry/` and `children/sophie/` are the canonical, shared-core versions. Don't
edit them expecting it to affect either live chart.
